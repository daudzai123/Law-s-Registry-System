# Law-MIS backup and disaster recovery

Each completed backup is one ZIP64 package in \`backup.path\`, named \`law-mis-backup-{backupId}.zip\`. It contains \`manifest.json\`, \`database/lawmis.dump\` (PostgreSQL custom format), and \`attachments/...\`. The package is built on disk and renamed atomically from a \`.zip.part\` file; incomplete parts are never recorded or accepted.

The manifest contains the package ID, format version, database checksum, application version, attachment count, total bytes, and a SHA-256 and size for every attachment. Restore accepts only version 2 packages. Paths are relative and are rejected if absolute, traversal-based, or outside the staging directory. Checksums and counts are verified before the live database or attachment directory is changed.

Restore first creates a complete \`pre-restore-{backupId}.zip\` safety package from the currently running database and attachment tree. If that safety package fails, the requested restore does not start. The database is restored with \`pg_restore --clean --if-exists --exit-on-error --single-transaction\`. Attachments are extracted and verified in a temporary directory on the attachment volume, then the live attachment directory is renamed aside and the verified directory is activated. The old directory is removed only after activation and service path refresh. If activation fails, the old directory is put back. Database rollback is handled by PostgreSQL's transaction; filesystem rollback handles directory activation.

The server-side restore endpoint (\`POST /api/backup/restore/{fileName}\`) is the preferred method for large packages and does not send the package through the browser. External packages use \`POST /api/backup/restore/upload\` with one multipart field named \`backup\`. Database-only files and the previous two-file format are rejected to prevent mismatched records and attachments. Downloads stream directly from disk.

Friday backups run at 02:00 in \`Asia/Kabul\`; startup and hourly checks catch up the latest missed Friday. \`BACKUP_WEEKLY_ENABLED\`, \`BACKUP_WEEKLY_ZONE\`, and \`BACKUP_PROCESS_TIMEOUT_SECONDS\` configure this. Keep the backend, PostgreSQL, backup directory, and attachment directory on persistent storage. Run one backend instance for scheduled backups. PostgreSQL tools are selected from \`PG_DUMP_PATH\` and \`PG_RESTORE_PATH\`, PATH, or the newest Windows installation.

The backend uses an operation lock so backup, restore, and deletion cannot overlap in one instance. The UI requires explicit restore confirmation and offers both an existing server package and an external package upload. The upload limit is 2 GB per multipart file and 4 GB per request; server-side restore is required for larger backup sets.

For recovery, choose the newest complete package, confirm its manifest and checksums, and restore it from the server. If a requested restore fails before activation, the live system remains unchanged. If a failure occurs after database activation, restore the generated \`pre-restore-*.zip\` package. To manually inspect a package, run \`pg_restore --list database/lawmis.dump\` after extracting it and compare every attachment's size and SHA-256 with \`manifest.json\`. Never restore a package with a missing manifest, missing attachment, count mismatch, checksum mismatch, or unknown version.
